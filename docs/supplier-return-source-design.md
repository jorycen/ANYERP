## 根因

- Web对所有completed入库单显示退库入口，但详情仅对采购入库返回return_sn_options，销售退货入库因此出现可点击却无SN选项。
- 现有requestReturn把原入库单store_id作为实际出库门店，供应商及采购关联从purchase_request_id取得。调拨和销售退货入库没有该采购关联。
- 单纯为销售退货入库添加SN列表，会产生供应商空、原采购空、金额可能为0的退库；并且不能从原仓扣已经调到其他门店的SN。
- 原采购退库流程执行后可能生成待重新入库周期，并非可对所有批量来源直接套用的供应商退款流程。

## 已完成的入口修复

后台统一提供can_request_return与supplier_return_reason；现有采购凭证退供应商入口仅针对已完成且关联原采购申请的采购入库。Web按后台能力显示入口，详情解释原因，requestReturn同时拒绝错误来源。未修改本单库存、单据、成本或审批。

## 待确认实施任务包

- 任务目标：从当前实际库存发起可追溯的供应商退货，支持跨店调拨、销售退货及批量入库来源。
- 使用对象：有当前门店库存权限的员工、仓管及现有采购/财务审核人员。
- 输入：当前SN/库位、完整库存周期、最初来源单、供应商依据及退货原因。
- 核心变量：实际出库门店与来源门店分开；来源类型（采购/批量）、供应商、实物用途（退货/返修/换货）与财务金额明确区分。
- 最小路径：在当前SN库存发起→后台追溯来源→展示可确认供应商及财务依据→复用适用审批→锁定当前SN和库位执行出库。原采购来源继续复用现有采购处理服务；批量来源不能伪造采购单或自动产生负应付。
- 输出：申请明细、来源证据、审批结果、实际库存出库流水及独立的财务处理状态。
- 验收：已调拨库存从当前门店扣减；不可用/已售/在途/已退SN不可再退；批量来源需明示无原采购财务凭证；重复提交/执行不重复扣库存；历史销售退单不被改成供应商退货。
- 不要做：直接把本单门店改回万象城、把旧来源伪造成采购、默认0元退款、跳过审批或现在执行本单。
- 待确认：流程实施范围，以及批量来源下退货、返修、换货的财务处理边界；本单供应商实际接收方式及实际可退金额另行核实。
- 建议下一步：用户确认流程后开发完整能力，测试通过后再另行处理本单。
